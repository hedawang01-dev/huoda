# 活搭 HUODA 5.4 项目检查报告

检查日期：2026-09-12  
检查基线：`v5.3-stable`（提交及标签 `6a95a0a`）  
目标：在保留 5.3 的页面、桌面端/移动端布局、导航、消息体验和既有功能前提下，升级为可接 Supabase、GitHub 与 Vercel 的真实业务闭环版本。

## 结论

5.3 是一套结构清楚、测试覆盖较好的响应式单页 Web App，但当前仍是“云端能力已预埋、本地演示数据为默认”的状态。代码不能直接作为真实线上业务投入使用，主要原因不是 UI，而是生产配置、认证入口、数据访问边界和业务状态机尚未收口。

本次升级应保留原生 HTML/CSS/JavaScript，不改成 React/Vue；继续使用同一个 `index.html`、同一套路由和同一套 Service，使 PC 与手机天然共享业务逻辑。云端数据必须由 Supabase Auth、PostgreSQL/RLS、Realtime 和 Storage 提供，页面只调用 Service，不直接查询表。

已检查根目录入口与配置、全部 CSS、`src/core`、`src/services`、`src/pages`、独立 `admin`、全部 Supabase SQL/迁移/Edge Function、构建与本地服务脚本、测试文件和文档引用。

## 持久化、共享与刷新

PC 与移动端共用同一份 HTML、JavaScript、Service 和状态对象，差异主要由 CSS 断点和布局包装实现，不存在两套业务代码。这一点应继续保留。

本地模式的数据可在同一浏览器恢复，也通过 Web Locks 和 `storage` 事件处理部分跨标签同步；它不是真实账户系统，也不能在手机与电脑之间同步。云端模式具备 Supabase 会话恢复、RLS、RPC、Realtime 和轮询兜底的代码基础，但因真实项目未创建，只验证了本地 PostgreSQL 内核和模拟 SDK 合同。

发布草稿和聊天草稿刷新后可恢复；搜索筛选、消息子标签等临时 UI 状态没有全部写入 URL，刷新后会回到默认值，属于可接受的界面状态，不应当与业务持久化混为一谈。

## 代码边界问题

1. `app.js` 同时负责页面模板、路由、本地数据库、登录流程、会话恢复和账户数据聚合，职责过多。5.4 只迁移与本次云端化直接相关的数据访问，不拆掉现有渲染框架。
2. `loadData()` 在页面主文件中直接查询 applications、reports、notifications、reviews、tasks；应由统一账户数据 Service 返回原子快照。
3. `authSubmit()`、`logout()` 直接调用 `sb.auth`；应由 `authService` 接管。
4. `messages.js` 直接查询 notifications/reports；应改为通知/账户 Service。
5. `community.js` 的举报和任务修改包含直接 RPC/本地写入；应分别进入 reportService/taskService。
6. `favoriteService` 已存在且在使用，不是失效 Service，但游客收藏及登录合并与新需求冲突。
7. `locationService`、`recommendationService` 都在使用；规则推荐不是 AI 概率，应继续按规则分描述。
8. 少量 5.3 兼容函数和空值保护仍留在 `app.js`，没有造成控制台错误；可在业务迁移后再删除已确认无引用的代码，不进行与 5.4 无关的大重构。

## 数据库与业务状态缺口

当前数据库的任务约束为 `open/paused/closed/completed`，报名约束为 `applied/accepted/rejected/completed/cancelled`。直接改前端文字无法形成可靠生命周期，因为并发录用、名额扣减、取消归还、审核通过、下架和消息权限都必须由数据库事务约束。

5.4 采用以下规范值：

- 兼职：`draft`（草稿）、`pending_review`（审核中）、`recruiting`（招聘中）、`full`（已招满）、`ended`（已结束）、`taken_down`（已下架）。
- 报名：`applied`（已报名）、`viewed`（商家已查看）、`communicating`（沟通中）、`accepted`（已录用）、`rejected`（未录用）、`completed`（已完成）、`cancelled`（已取消）。

旧任务状态必须通过增量迁移映射，不能删除旧迁移或重新初始化现有库。录用、取消、结束和审核动作必须走带行锁的 RPC；前端不能直接修改状态列。

## 安全与生产部署问题

- `config.js` 已忽略提交，示例只包含 URL 和 publishable/anon key，未发现 Service Role、数据库密码或私钥写入源码。
- 公开 key 可以存在浏览器端，但所有数据安全必须依赖 RLS；Service Role/Secret key 只能放在 Supabase 服务端或 Vercel 服务端环境，不能进入静态文件。
- 当前缺少 `dist` 生产目录、构建脚本、Vercel 输出配置和生产缺失配置拦截。若原样发布，`config.js` 缺失或为空会让公网网站进入本地演示，这是生产风险。
- `index.html` 资源路径大小写目前与磁盘文件一致；Hash 路由 `#/...` 刷新可由静态托管稳定处理。`/admin/` 需要明确 rewrite。
- 本地预览服务器已有资源白名单，不会暴露 SQL、测试、Git、环境文件和服务端函数源码；Vercel 也应只发布 allowlist 构建出的 `dist`。
- `.gitignore` 范围偏小，需要覆盖 `.env.*`、Vercel/Supabase 本地目录、构建产物、编辑器缓存和证书密钥，同时保留安全的示例文件。

## 5.4 实施边界

本次做增量升级：新增数据库迁移和 Service，替换页面中的直接数据访问，扩展现有状态控件，增加生产构建与部署检查。保持现有 DOM 主结构、品牌样式、断点、导航和页面路由。支付、资金托管、短信登录、地图选点、复杂客服工单和高级运营报表不进入 5.4。

真实 Supabase、GitHub 和 Vercel 项目创建前，项目将保持显式本地演示模式供验收；生产构建在缺少公开云端配置时必须失败，避免把演示库误发布为正式网站。
